# Access Module (P5 Parental Controls)

- **Profile IDs are `string` UUIDs**, never `int`. `profile_id` columns are `CHAR(36)` matching `user_profiles.id` (migrations `061_access_schedules.sql`, `062_profile_tags.sql`, `063_device_stream_limits.sql`). All `src/Access/` service methods take `string $profileId`; `ProfileStreamLimit::fromRow()` narrows with `is_string()`, not `is_numeric()`.
- `RequestContext::setProfileId(?string)` / `getProfileId(): ?string` — the request-scoped profile id is a UUID string (`src/Server/Http/RequestContext.php`).
- **Services** (`src/Access/`): `AccessScheduleService` — time-window access control, `isAccessAllowed()` returns false when an active schedule matches (middleware responds 403). `ProfileTagService` — `blocked`/`allowed` tag lists (`ProfileTag::TYPE_BLOCKED`/`TYPE_ALLOWED`); tag filtering is applied in `ItemRepository::query()` from the `RequestContext` profile id. `StreamSessionService` + `ProfileStreamLimit` — per-profile concurrent-stream caps backed by `profile_stream_limits` and `active_streams`.
- **Routes**: `/api/v1/profiles/{profileId}/schedules`, `/tags`, `/stream-limits`, `/active-streams` are registered in `src/Server/Core/Application.php` via `$router->group('', $cb, [new AuthMiddleware()])` — always gate these behind `AuthMiddleware`; `AccessScheduleMiddleware` and `StreamLimitMiddleware` run globally after auth.
- **The tag type arrives under TWO spellings and both are load-bearing — this is not redundancy to tidy away.** `ProfileTagController::createForProfile` reads `$this->validateTagType($data['tag_type'] ?? $data['type'] ?? null)` (`ProfileTagController.php:127`). `phlix-ui/src/api/admin/users.ts:651` posts `{tag, tag_type}`; `phlix-console-client/src/Api/Admin/AdminClient.php:566` posts `{tag, type}`. A rename in either direction does not remove the 400, it moves it to the other client. `tag_type` **wins when present** so an explicitly invalid `tag_type` is refused rather than falling through to a stale `type` — `testAnInvalidTagTypeDoesNotFallThroughToAStaleTypeKey` pins it on the absence of the `INSERT INTO profile_tags`, not only on the 400, and `testTheAdminSpaTagPayloadCreatesATag` / `testTheConsoleClientTagPayloadStillCreatesATag` pin one spelling each. Precise limit of `??`: a literal `null` `tag_type` still falls through to `type`; only a non-null invalid value is refused. **This applies to the tag-type field only** — schedule create accepts snake_case alone (`start_time`, `end_time`, `days_of_week`, `is_active`; `AccessScheduleController.php:132-135`).
- **Create responses carry the new id under BOTH the new `id` and the legacy key**, for the same reason: tags return `{id, tag_id, message}` (`ProfileTagController.php:151-152`), schedules `{id, schedule_id, message}` (`AccessScheduleController.php:161-162`). `phlix-ui` declares `Promise<{ id: number; message: string }>` for both (`users.ts:606`, `:650`) and read `undefined` before `id` existed; the console client reads only `message`. Adding a key breaks nobody; dropping one could break a consumer nobody has enumerated. `testTagCreateReturnsTheNewIdUnderBothIdKeys` / `testScheduleCreateReturnsTheNewIdUnderBothIdKeys` redden if a legacy key is dropped.
- **`profile_id` is emitted as the CHAR(36) UUID string, never cast.** `AdminProfileController::createForUser` returns `'profile_id' => $newId` uncast (`:166`) because `UserProfileManager::create()` is typed `: string` (`src/Auth/UserProfileManager.php:386`) and returns the UUID it generated. This is the string-UUID rule above at its concrete failure point: `(int)` on a UUID is `0`, or a truncated leading digit run — a 201 carrying an id that addresses no row. `git grep '(int) $newId' src/` is empty; keep it so. Pinned by `testProfileCreateReturnsTheUuidTheManagerGenerated` and `testProfileCreateDoesNotTruncateAUuidThatBeginsWithDigits`. `AdminUserController::create` is the counter-example: its **code is correct** (`'user_id' => $userId`, `:295`) while its docblock still declares `user_id: int` (`:235`) — a docblock lie over correct code, not a regression; never "fix" that code to match its docblock.
- 🚨 **A fixture is a claim about who calls you.** With the `$data['type']`-only defect fully reinstated, all **53** pre-existing tests over these controllers stayed green (`ParentalControlsAuthorizationTest` 28 + `Admin/AdminProfileControllerTest` 25) — its single tag-create fixture posts `['tag' => …, 'type' => …]` (`ParentalControlsAuthorizationTest.php:376`), the one key the SPA never sends, and the profile-create happy path asserted only `assertArrayHasKey('profile_id')`, which is true of `0`. Any new test over these controllers must use a payload shape a **real named client** actually sends: `phlix-ui/src/api/admin/users.ts`, `phlix-console-client/src/Api/Admin/AdminClient.php`, `phlix-mobile-client/src/api/ParentalControlsManager.ts`, `phlix-roku-client/source/lib/ApiClient.brs` (+ its caller `components/ParentalControlsScene.brs`).
- ⚠️ **KNOWN-BROKEN, deliberately not fixed — mobile and Roku creates still 400.** Two of the four clients work, not four. Both post **camelCase** keys the server never reads: mobile `addTag` sends `tagType` (`ParentalControlsManager.ts:99`) and `createSchedule` forwards `startTime`/`endTime`/`daysOfWeek`/`isActive` verbatim (`:44-49`); Roku posts `{tag, tagType}` (`components/ParentalControlsScene.brs:359`). Rooted upstream in `phlix-contracts/src/ProfileTag.ts`, which declares `tagType` and types `profileId: number` when the column is `CHAR(36)`. Tracked as S234; clients pin `@phlix/contracts` **by tag**, so the fix is a contracts release plus a per-client bump, not a merge. Fix tags *and* schedules for *both* clients in one pass or not at all — a lone `tagType` alias makes tag create work while schedule create keeps 400ing, which reads as "mobile fixed". 🔎 Correction to the S234 note: Roku's `createProfileTag` is **not** unwired — `components/ApiTask.brs:668` dispatches it and `components/ParentalControlsScene.brs:354-359` builds the payload (also true at the SHA S234 measured), so Roku is reachable-and-broken, not dead.
- DB access follows the repo-wide rule: `Workerman\MySQL\Connection` with parameterized `?` placeholders only.
